# 安卓端功能对齐清单（2.0 原生 vs 1.1.0 Flutter）

> **这份清单解决什么问题**：`NATIVE-2.0-PLAN` §10 的 Phase 4 完成条件是「功能对齐清单逐条打勾
> （与 Flutter 版逐页对照）」。在此之前它不存在，于是「哪些页面对齐了」全靠记忆 ——
> 而记忆在这个项目里已经被证伪过很多次（「状态层齐了、界面没接」出现过 8 次以上）。
>
> **证据等级（每一行都必须能落到出处，落不到就标 ❓）**
>
> | 标记 | 含义 |
> |---|---|
> | ✅ | **真机验过**：有脚本输出、像素/控件树证据或提交里的实测记录 |
> | 🟡 | 代码在、编译过、单测过，**但真机上没人看过** |
> | ⬜ | 明确没做 |

## 三、**没人查过**的（❓ —— 下一轮优先把这些变成 ✅ 或 ⬜）

> **第 23 轮进展**：1 与 3 已结案（见下），2、4、5 仍未执行。

1. ~~**图片缓存固定保留最近 20 张**这个契约在原生端是否真的生效~~ → **✅ 已结案（第 23 轮，代码取证）**：
   **这条在 2.0 里没有对应物，而且不需要有。**
   * 原生安卓端**不落盘图片**：唯一写图片字节的地方是
     `capture/CaptureService.kt:426 dumpForAcceptance()`，而它**只在 debuggable 构建**里落一帧
     取证图（`files/capture-last.jpg`），正式形态直接内存 → 上传。
   * 三条采集路径（相机 / 相册 / 悬浮球截屏）都是「取字节 → 上传 → **主机**持有」，
     图片按内容寻址存在主机侧，手机按需从主机取。
   * **规格附录 A 第 18 条（"固定留 20 张、去掉缓存选项"）在 2.0 里失去对象** ——
     它针对的是 1.1.0「手机本地也有图库缓存」那种形态。
   * 顺带一条**要留意的差异**：Windows 侧**有**可配置的 `ImageCacheLimit`（设置页给到「120 张」），
     那是**主机**保留多少张自己的截图 —— 与"手机缓存上限"不是同一件事，不要混为一谈。
2. **`MathText` 在真机上对用户真题（15 条记录 / 59 题）的渲染**：裸化学式 36 处、空格对齐表 4 题、行内公式最长 84 字符 —— 这些数字来自 1.1.0 的真实数据，原生端**没有拿同一批数据跑过一遍**。（**部分覆盖**：第 18 轮已把最"数学密集"的一题原文做成 6 条解析回归，并抓出 `\mathbb N` 缺陷，已修；但**渲染层**仍未用真实数据在真机上看过。）
3. ~~**多页识别的上限 6 与"同图同页序复用"**在原生端的行为~~ → **✅ 已结案（第 23 轮，代码取证）**：
   * **上限 6 是硬夹取**，不是只限制 UI：`ui/QuizViewModel.kt:1488 const val HARD_MAX_PAGES_PER_TASK = 6`，
     两处 `coerceIn(1, HARD_MAX_PAGES_PER_TASK)`（`:1139` 设置写入、`:1433` 读取），
     设置页滑块同样以 `RecognitionSettingsScreen.kt:81 HARD_MAX_PAGES = 6` 为界。
   * **"同图复用"是主机侧按内容寻址做的**，两段都有真主机 E2E 钉着
     （`android/core/src/test/.../HostApiEndToEndTest.kt`）：
     `:187` 重复上传同一张图 → `existed = true`（内容寻址去重）；
     `:216` 同一个 `task_id` 再提一次 → `cached = true` 且状态已是 `done`（**不再跑一次识别**）。
   * **口径澄清**：复用判定只看**图片内容哈希 + task_id**，"页序"只影响提交顺序，
     **不参与复用判定** —— 所以契约里"同图同页序复用"的落地路径就是这两条，
     端侧不需要额外实现（原生端也确实没有 `cached`/`existed` 的消费代码）。

4. **配对页重做后的三种方式在真机上的实际可达性**（扫码需要相机权限；粘贴需要剪贴板内容；手输需要真主机）。
5. **深色 + 动态取色同时开启**时的观感（两份设置相互影响，没人组合验过）。

### 第 89 轮：对齐清单 ❓#4 结案 —— 配对页三种方式**都可达**（真机证据）

| 方式 | 怎么验的 | 结果 |
|---|---|---|
| **方式一：扫码** | 在配对页点「开始使用（扫码配对）」 | ✅ 弹出**系统相机权限框**：「允许"AI 双端搜题（开发版）"拍摄照片或录制视频？」，前台窗口 `com.lbe.security.miui/…GrantPermissionsActivity` |
| **方式二：粘贴配对链接** | 用 `am start -d 'quizsync://pair?host=…&port=…&code=…'` 触发深链 | ✅ 表单被**预填**（地址/端口/配对码），点一下「开始配对」即成功 |
| **方式三：手动输入** | 逐字段输入（点号用 `KEYCODE_PERIOD` 无效，见下）+ `ENTER` 提交 | ✅ 配对成功（屏幕上确认「已连接 TIOPWXNL」） |

**与页面文案一致** ✓：页面自己写着「点击下面的按钮**才会**申请相机权限并打开扫码。
**不授权也不影响配对**：方式二 / 方式三随时可用」—— 实测正是如此（权限只在点按那一刻申请）。

**我做了什么、没做什么（留痕）**：
* 弹框时我点了**「拒绝」**（**没有授予相机权限**，保持原状）；
* 拒绝后仍在配对页、三个方式都还在 ✓；
* 因此设备状态与我接手时一致（`CAMERA: granted=false`）。

**顺带记下一条实测**（写进 ❓#4 的备注）：**在这台 MIUI 设备上，用 adb 无法输入 IP 里的点号** ——
`input text` / `input keyboard text` / 逐字符 `keyevent` 三种通道都会把 `.` 变成全角 `。`
（详见第 26–34 轮的记录）。所以**方式三在自动化下只能用不含点号的主机名**（但那又解析不了），
真正可用的自动化路径是**方式二（深链预填）**。

### 第 93 轮：新增一条**双端差异**记录（写测试时查出来的）

| | 安卓（Kotlin） | Windows（C#） |
|---|---|---|
| 解析产物 | `MathSpans` / `MathFraction`（**只有两个子类型**） | `MathText` / `MathFraction` / `MathRoot` / `MathBigOperator` / `MathScripted` |
| 上下标 | **展平成带 `Script` 的 `MathSpan`**，不是结构节点 | 保留为 `MathScripted` 结构 |
| 根号 / 大型运算符 | 在解析期就落成文本/符号（无独立节点） | 保留 `MathRoot` / `MathBigOperator`（含上下限） |

**来源**：第 92 轮给安卓侧补真实真题回归（`RealDataMathTest`）时，`when (piece)` 编译报错暴露出
两端的 `MathPiece` 家族不同 —— 不是猜的，是编译器逼出来的。

**为什么必须记下来**：
* **"两端公式渲染一致"不能从解析层假定** —— 两边拿到的是**不同形状的中间表示**；
* 一致性只能在**渲染结果**上比（真机截图 / Windows 截图），而那需要人眼看图（我读不了图片）；
* 这也解释了为什么两端的**降级行为**可能不同：安卓在解析期就把不认识的东西落成文本，
  C# 会保留结构到渲染期再决定怎么画 —— 遇到"少数派写法"时，两端表现不保证同步。

**待办（需要人眼）**：拿**同一段真实公式**（例如那道数列大题）在两端各截一张图，逐项对照
（分数是否都画了分数线、上下标位置、根号形态）。这是 Phase 6「悬浮窗观感逐条对照」之外
**另一处必须人眼的一致性检查**，之前没被列出来过。
