## 一、怎么开 TalkBack 与深色

```powershell
# TalkBack（需要设备上已装 Google 无障碍套件；没有就跳过本文件第一节，并如实记「无 TalkBack」）
adb shell settings put secure enabled_accessibility_services com.google.android.marvin.talkback/com.google.android.marvin.talkback.TalkBackService
adb shell settings put secure accessibility_enabled 1
# 关掉
adb shell settings put secure accessibility_enabled 0

# 深色：直接切系统的夜间模式，再看应用「跟随系统」时是否正确
adb shell cmd uimode night yes
adb shell cmd uimode night no

# 截图取证（每页浅/深各一张）
adb exec-out screencap -p > D:\DeepseekHarness\TemporaryConversationFile\images\dark-<页面>.png
```

> ⚠️ **验完把系统夜间模式与无障碍开关复位**（`night no` / `accessibility_enabled 0`）。

### 第 65 轮更正：上一轮的「悬浮球颜色随主题变」是**我的测量错误**（结论撤回）

第 63 轮我看到球的合成色在浅色下 `(103,175,111)`、深色下 `(67,139,74)`，据此写了"推翻 B11"。
**这是错的** —— 球带透明度（默认 `opacity = 0.85`），落在不同底色上**本来就会**呈现不同合成色。

反解验证（同一元素、同为 6121 像素）：

```
由 obs_light - obs_dark = (1-α)(bg_light - bg_dark) 逐通道解 α：
  R: 36/238 → α = 0.8487
  G: 36/234 → α = 0.8462
  B: 37/239 → α = 0.8452        ← 三通道一致，且正是球的默认 0.85

用 α = 0.85 反解球自身的填充色：
  浅色底 → (76,161,86)
  深色底 → (76,160,84)          ← 两种底给出同一个值
```

**结论**：球的填充色**与主题无关** ✓ —— **B11 原描述成立**，第 63 轮那条"新发现"作废。
（两种底之间的 1–2 个色阶差异来自取整与截图压缩。）

**留下的是方法教训（比结论更值钱）**：
> **带 alpha 的元素不能用截图原始像素跨背景比较** —— 必须先反解出元素自身的颜色，
> 或固定在同一种背景下比。否则"半透明压在深底上变暗"会被误读成"元素自己变色"。

这条与本项目已有的另一条纪律同类：「探针自己要先怀疑」（本项目的 §DPI、§全角点号、
§状态栏 chunked 都是同一个模式：**先把测量方法验证一遍，再下结论**）。

### 第 67 轮：B6 的另一半 —— 琥珀色**确实**随主题变（与绿色不一致）

同机同页（设置页）、只切主题，琥珀色像素统计：

| | 浅色 | 深色 |
|---|---|---|
| 琥珀色 | `(223,164,56)`，**3344 px** | `(243,206,73)`，**3303 px**（更亮） |
| 页面底色 | `(255,255,255)` | `(17,21,16)`，42641 px ✓ 确认切了主题 |

**先做透明度验算（上一轮的教训）**：若它是半透明压在两种底上，应满足
`obs_light − obs_dark = (1−α)(bg_light − bg_dark)`。实测 R 通道 `223 − 243 = −20`
⇒ 反解 `1−α = −0.084`，**负值在物理上不可能** ⇒ **这不是合成效应，是元素自己换了颜色** ✓

### 结论：B6 的两半**不一致**

| 标注色 | 跨主题行为 | 判定 |
|---|---|---|
| 绿色（两种色调，168 px / 83 px） | `(97,202,81)` / `(92,199,110)` **逐字节相同** | 不漂移 ✓ |
| 琥珀色 | `(223,164,56)` → `(243,206,73)` | **会漂移** ✗ |

**这需要定性（写清不确定处，别过度断言）**：
* **不确定**：我量到的这个琥珀是**设置页的警示文案色**（「受限于网络延迟…不建议开启」），
  **还不确定它是否就是答案标注用的那个"标黄" token** —— 要下结论必须先在**结果页**量到标黄。
* 若两者是同一个 token：则"信息色跨主题必须一致"这条要求**只做到了绿色那一半**；
  但反过来说，深色下用更亮的琥珀是标准的对比度做法 —— 所以这更像是
  **口径本身需要写清**（"信息色"到底要求"逐字节一致"还是"可辨且同色相"），而不是实现有错。
* 若两者不是同一个 token：则本条只证明"警示色随主题自适应"，与 B6 无关。

### 第 75 轮：B5 / B7 的**代码级**结论（失败模式被构造排除）

B5（深色下 1px 描边）与 B7（深色下表格层次）是观感项，但它们的**失败模式**（描边/分割线在深色下
看不见、表格糊成一片）可以从代码上判定 —— 关键是这些描边色是"随主题变"还是"写死"：

```
ui/components/MathText.kt:341   val outline = MaterialTheme.colorScheme.outlineVariant   ← 表格分割线
ui/theme/QuizTheme.kt:88        浅色 outlineVariant = #FFC1C9BE
ui/theme/QuizTheme.kt:127       深色 outlineVariant = #FF414941   ← 深色下是**另一套值**
ui/theme/QuizTheme.kt:194/220   浅色 cardStroke = #FFE3E7E5  /  深色 cardStroke = #FF2A2F33
                                （analysisStroke、materialStroke 同样各有深色变体）
```

**结论**：
* 表格分割线取自 **Material 主题语义色** `colorScheme.outlineVariant`，而该值在浅/深调色板里
  **分别定义了不同颜色** ⇒ **深色下表格必然有可见的分割线**，"糊成一片"这一失败模式**构造上不成立** ✓
* 同理，卡片描边（`cardStroke`）、解析描边（`analysisStroke`）、材料描边（`materialStroke`）
  **都有显式的深色变体** ⇒ B5 的失败模式（深色下 1px 线消失）**同样被排除** ✓

**仍未证的部分（诚实划界）**：以上只排除了"消失/糊掉"，**没有**证明"深色下的对比度是否舒服"
（`#414941` 与深色底 `#111510` 的对比是否偏弱、是否刺眼）—— 那仍然是**观感，需要人眼看图**。
判据升级顺序建议：先排除失败模式（本轮已做，可复现），再看观感（人眼，不可自动化）。

### 第 77 轮：B10（转场是否闪白）**通过** —— 逐帧证据

单张 `screencap` 抓不到闪帧（一次要 300–500ms），改用录像 + 逐帧量亮度：

```
深色主题下 screenrecord 8 秒（期间来回切 历史记录 / 当前任务 / 设置 共 12 次）
→ ffmpeg -vf fps=10 抽帧 → 79 帧
→ 每帧算全图平均亮度（0.2126R+0.7152G+0.0722B）
```

| 指标 | 实测 |
|---|---|
| 帧数 | **79**（10 fps × 7.9 s） |
| 亮度范围 | **22 – 27**（全暗） |
| 最亮帧 | **27.3**（`b10-053.png`） |
| 对照 | 若发生闪白，该帧亮度会是 **~250**（浅色页面的量级） |

**结论 B10 ✅**：深色主题下切页**没有白闪** —— 79 帧里没有任何一帧的亮度接近浅色量级。

**判据的边界（如实写）**：10 fps 抽样 ⇒ 只能保证**≥100ms 的闪白会被抓到**；
单帧级（~16ms）的瞬时白闪理论上可能漏掉。Android 的窗口/Activity 过渡本身在 200–300ms 量级，
若发生"主题白闪"必然落在采样窗口内，所以这条对这个失败模式是有效的；
但要宣称"任何瞬时闪白都没有"，需要 60fps 采样（可用 `screenrecord --bugreport` 或更高帧率重录）。

**顺带**：本轮的录像/抽帧方法对"过渡类观感项"是通用的 —— 之后 Phase 6 的悬浮窗动效对照
如果需要客观判据，可以复用同一套（录像 → 抽帧 → 逐帧量指标）。
