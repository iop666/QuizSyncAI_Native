# versions —— 协议版本与现状材料

## 现状材料（输入区）

`v1-input/` 是**从现有 Flutter 版实现反推现状**的输入材料：四份现有契约（功能规格 / 协议 / 数据模型 / AI 契约）的副本，已剥离实现绑定（技术栈、包名、仓库内路径），**语义未改动**。

- 来历、原始提交、剥离规则与逐文件改动清单：见 [`v1-input/README.md`](v1-input/README.md)。
- 原文件仍在产品仓库里，**这里的是副本**；两份内容若不一致，以 `v1-input/README.md` 记录的原始提交为准。

## 版本纪律

- **v1 = 现状**：v1 不是一个「设计」，而是对已发布行为的忠实记录。写 v1 快照时**不许顺手改良**：所有看起来不干净但已被用户接受的行为（不对称语义）照原样记录。
- **v2 = 只增不改**：v2 在 v1 之上新增能力；v2 服务端必须能回答 v1 客户端的兼容子集。
- 冻结 = tag。冻结后改语义 → 只能进下一个主版本。

## v2 的记录形态（2026-09 决定，取代上面的 `v2-draft/` 目录）

v2 **不再单独建一个草案目录**，因为它已经被两处更准确的地方承载，再开一份必然漂移：

| v2 的哪一部分 | 记在哪里 | 为什么 |
|---|---|---|
| **已实现**的部分 | 直接进规范正文：新增 `spec/12-provider.md`（Provider 域），另在 `spec/08-tasks.md` / `10-versioning.md` / `11-capabilities.md` 里以逐句 **v2 目标** 标注未实现项 | 规范正文是「MUST/SHOULD + 字段表 + 数值表」的地方，三端照它实现；已实现的行为放这里才有裁判力 |
| **未冻结**的部分（已落地但还没向量、或仍是方向） | `CHANGELOG.md` 的 `[Unreleased]` 小节，其中**「已落地」与「v2 目标」分开列** | CHANGELOG 是协议版本的唯一声明处；「已落地 ≠ 已冻结」这条区别必须有地方写 |
| 未实现的变更方向 | 同上的 `v2 目标` 条目（逐条不得写成已实现） | 见 `CHANGELOG.md` 开头第 2 条纪律 |

**代价要写清楚**：`spec/` 里因此出现了「同一个文件既有现状、又有 v2 目标」的写法。
这是有意的取舍 —— 拆成两份的代价（两处维护、必然漂移、读者不知道信哪份）比混排更大；
每一条 v2 目标都带显式标记，且 `spec/README.md` 的状态表会写明哪个文件含 v2 域。
