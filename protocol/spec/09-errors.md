# 09 错误码

> 状态：v1 现状（**按实现反推**）+ v2 目标（标注清楚哪句是现状、哪句是 v2 变更）。
> 强制级别：**MUST** = 必须做到；**SHOULD** = 有理由才能偏离；**MAY** = 可选。
> 未标「**v1 现状**」或「**v2 变更**」的条目 = v1 现状且继续有效。本文件是错误码的**唯一全表**：`code` ↔ HTTP 状态 ↔ 可重试性 ↔ `retry_after_seconds`。

## 1. 规则

### 1.1 错误体形状

- **MUST** 错误响应体是 UTF-8 JSON 对象，**恒含三个键**：`{"code": <字符串>, "message": <字符串>, "retry_after_seconds": <整数或 null>}`；不需要等待时间时该键**仍然出现**、值为 `null`。
- **MUST** 错误响应 `Content-Type: application/json; charset=utf-8`（与成功响应一致）。
- **MUST** HTTP 状态码与 `code` **成对出现**（对应关系见 §3，不得出现同一码两个状态）。
- **MUST** 等待时间只走响应体的 `retry_after_seconds`（正整数、单位秒）；**v1 现状** 不使用 `Retry-After` 响应头。
- **MUST** 除 `/ws` 外，所有响应（**含**错误响应）都带 `X-QS-Server-Version: <主机版本>`；**v1 现状** `/ws` 完全绕过中间件，其握手失败响应**不带**该头（见 `02-transport.md`）。
- **MUST NOT** 在成功响应里塞 `code` / `message`；**v1 现状**唯一例外是重复配对的 409（见 `03-auth-pairing.md` §3）。

### 1.2 分支与废弃

- **MUST** 客户端按 `code` 分支，HTTP 状态码只作辅助判据。
- **MUST NOT** 按 `message` 文本分支：同码多种 message 已存在，措辞**不是契约**（`message` 只用于展示）。
- **MUST** 客户端容忍未收录的 `code`：按「通用失败」处理、显示 `message`、保留原始 `code` 便于排查；**MUST NOT** 因收到陌生码而崩溃、静默吞掉或当成成功。
- **MUST** 已发布的 `code` **不得删除、不得改语义**，只能标记废弃。
- **v2 变更** 错误体新增 `deprecated` 标记与替代码字段；被废弃的码至少继续返回一个大版本，客户端在此期间必须同时认识新旧两码。

### 1.3 可重试性判据

- **MUST** 「可重试」= 在等待 `retry_after_seconds`（或用户修正输入、主机状态变化）之后**重发同一请求**有意义；「不可重试」= 相同请求重发**必然**再次失败。
- **MUST** 401 / 403 / 404 / 413 / 426 一律**不自动重试**：分别需要重新配对、改权限、改目标、改体积、升级版本。
- **MUST** 400 不自动重试（请求构造错了，重发结果不变）。
- **MUST** 429 可重试：**MUST** 等待 `retry_after_seconds` 秒后重试，**MUST NOT** 立即重试或忽略该值硬重试。
- **MUST** 409 `no_active_collection` 可重试，但**前提是主机状态变了**（用户选了合集），不是退避重试。

### 1.4 两个错误码空间

- **MUST** 区分两个取值空间：**HTTP 错误码**（§3 的全表，出现在错误响应体的 `code` 里）与**任务错误码**（出现在任务查询响应的 `error_code`、任务失败事件的 `error_code` 里）。
- **MUST NOT** 把任务错误码当作 HTTP `code` 来分支，反之亦然；两者字段名不同、出现位置不同。
- **v1 现状** `internal` 是**两个空间共用**的兜底值：它在任务错误码里表示「未分类失败」（例如离线补跑烧掉的死信 `queue_give_up` 是任务错误码，AI 类失败另有 `ai_timeout` / `ai_auth` / `ai_rate_limited` / `ai_bad_response` / `ai_quota_exceeded` / `no_question_found` 等取值）。
- 任务错误码的完整取值属任务与 AI 域，不在本文件覆盖范围；本文件只规定它与 HTTP `code` **不得混用**。

### 1.5 v1 现状的重试执行

- **v1 现状** HTTP 层**不做**自动重试（与 `02-transport.md` §1.7 同一口径）：失败直接交给上层。
- **v1 现状** 客户端只有**一条**自动补跑通路：把待上传的图片放进离线队列，等主机可达后按序补跑；补跑失败累计尝试次数，达到上限（5 次）该任务被标成死信（任务错误码 `queue_give_up`）。**入队条件按入口不同**：
  - 「截屏」入口：收到**除 `revoked`、`no_active_collection` 之外**的任何错误码都入队（**含** `413` / `429` / `400`），补跑时会再次失败——**这不是推荐做法**；
  - 「相册选图」入口：只在传输层异常时入队，拿到错误码就直接失败并提示。
- **v1 现状** 离线队列队满（20 条）时入队失败，界面提示「离线队列已满，请等 Windows 上线后重试」，**不静默丢弃**。
- **v2 变更** 只有传输层失败、`429` 与 `5xx` 入离线队列；4xx 直接失败并提示。HTTP 层只对 GET 与幂等 POST 退避重试（1s / 3s / 10s），4xx（除 408 / 429）不重试。

## 3. 错误码全表

| code | HTTP | 含义 | 可重试性 | `retry_after_seconds` | 客户端提示（v1 现状） |
|---|---|---|---|---|---|
| `unauthorized` | 401 | 没有 token（缺头/空值），或 token 与在册设备都不匹配；WS 握手失败同码 | 不可自动重试（需重新配对） | 无（`null`） | 无专用分支：显示服务端 `message` 原文 |
| `revoked` | 401 | token 命中在册设备，但该设备已被吊销 | 不可重试（需重新配对） | 无 | 「已解除配对，请重新扫码」，并清除本地配对信息 |
| `version_mismatch` | 426 | 请求带 `X-QS-Client-Version`，且其主版本与主机主版本不同 | 不可重试（需升级一端） | 无 | 显示服务端 `message`（内含双方版本） |
| `invalid_code` | 401 | 配对码与主机当前有效码不匹配 | 可重试（核对后）；**计入失败数** | 无 | 「配对码错误，请核对 Windows 端显示的 6 位数字」 |
| `code_expired` | 401 | 配对码已过期 | 可重试（主机刷新码后）；**计入失败数** | 有，语义见 §5 | 「配对码已过期，请在 Windows 端点『刷新』后重试」 |
| `rate_limited` | 429 | 三种触发：配对已锁定 / 配对尝试过于频繁 / 图片上传过于频繁 | 可重试（等 `retry_after_seconds`） | 有（三种都带） | 配对 429 →「尝试过于频繁，N 秒后再试」（N = `retry_after_seconds`，缺省 60）；上传 429 → 显示服务端 `message` 原文 |
| `invalid_request` | 400 | 请求体或字段/参数不合法 | 不可重试 | 无 | 显示服务端 `message` 原文 |
| `too_many_pages` | 400 | 单个任务的页数超过硬上限 6 | 不可重试（需减少页数） | 无 | 显示服务端 `message` 原文 |
| `no_active_collection` | 409 | 任务没落到任何合集（主机未选，或指定的合集在主机上不存在） | 视触发：用户选好合集后可重试 | 无 | **固定文案**「请先在电脑上选择任务合集」（**不**显示服务端 `message`） |
| `queue_full` | 429 | 主机排队中的任务已达深度上限 20 | 可重试 | 有（**固定 10**） | 显示服务端 `message` 原文 |
| `payload_too_large` | 413 | 单文件超过 2097152 字节 | 不可重试（需缩小后重传） | 无 | 显示服务端 `message` 原文（「单文件需 ≤ 2MB」） |
| `not_found` | 404 | 目标不存在：图片 / 任务 / 会话 / 合集（含图片 hash 形态非法） | 不可重试 | 无 | 显示服务端 `message` 原文 |
| `internal` | **无** | 兜底码：**没有可用 `code`** 时使用（v1 现状不由任何 HTTP 端点产生） | 视情况 | 无 | 显示本地兜底文案（如「HTTP 500」「未知网络错误」） |

## 4. 各码的 message 取值（v1 现状）

- `unauthorized`：「缺少 token」「token 无效」「WS 握手鉴权失败」
- `revoked`：「设备已被吊销」「WS 握手鉴权失败」
- `version_mismatch`：「客户端版本 X 与服务端 Y 主版本不一致，请两端都升级到同一大版本」
- `invalid_code`：「配对码错误」；`code_expired`：「配对码已过期」
- `rate_limited`：「失败次数过多已锁定」（配对锁定）／「尝试过于频繁」（配对滑窗）／「上传过于频繁」（上传滑窗）
- `invalid_request`：「body 不是合法 JSON」（配对、创建任务、推同步 op **三处**）／「字段缺失或格式错误」／「需要 multipart/form-data」／「文件内容为空」／「缺少 file 字段」／「task_id / image_hash 缺失」／「image_hash 未上传」／「ops 缺失」／「from_device 缺失」
- `too_many_pages`：「一次最多 6 页（当前 N 页）」
- `no_active_collection`：「请在电脑端先新建或选择一个任务合集」（未指定合集且主机未选）／「所选合集不存在，请重新选择」（指定的合集在主机上不存在）
- `queue_full`：「主机任务队列已满（N），请稍后重试」
- `payload_too_large`：「单文件需 ≤ 2MB」
- `not_found`：「图片不存在」「任务不存在」「会话不存在」「合集不存在」
- `internal`：无固定文案；出现在任务错误码的兜底位，以及客户端「错误体里没有 `code`」时的本地取值。

## 5. 触发顺序与易错点

- **MUST** 受保护路径上**鉴权先于版本协商**：token 无效时得到 `401 unauthorized`，不会因为版本不符改成 `426`。
- **MUST** `/ws` 不参与版本协商，也不经过中间件的响应改写：握手失败就是普通 `401` 响应。
- **MUST** 配对请求的处理顺序：JSON/字段校验（400）→ 锁定（429）→ 窗口限流（429）→ 码比对（401 `invalid_code`）→ 过期（401 `code_expired`）→ 签发。**锁定先于码比对**，故锁定期内**配对码正确也会被拒**。
- **MUST** `code_expired` 的 `retry_after_seconds` 在 v1 现状是「**已过期秒数**」截断到 `0..60`，**不是**剩余等待时间；客户端 **MUST NOT** 据此承诺「等这么久就能成功」。**v2 变更**：改为「需主机刷新配对码」的语义，或直接省略该字段。
- 三条 `429` 的 `retry_after_seconds` 口径不同：配对滑窗 =「最早一次尝试离开窗口的整秒（向上取整）」；配对锁定 =「剩余锁定整秒（向上取整）」；上传滑窗 =「最早一次上传离开窗口的整秒（向上取整）」；`queue_full` 则是**固定 10**。
- **MUST** 图片上传的 `413` 有**两条**产生路径：① 声明的 `Content-Length` > 2162688 时先拒（**不**解析表单）；② 边收边计数，累计字节一超过 2097152 立即拒（**不看总长**，分块传输时靠它兜底）。
- **MUST** 上传路径上**限流先于体积判定**：被上传限流时不会同时报 `413`；被拒（含 413 / 400）的上传**同样计入**限流额度。
- `404 not_found` 在图片下载上**不区分**「形态非法」与「不存在」：非 64 位小写十六进制的 hash 也回 `404`（避免泄漏文件系统信息）。
- **MUST** `409` 的**重复配对不是错误**：响应体没有 `code` 字段，客户端按成功处理（见 `03-auth-pairing.md` §3）。

## 7. 两套 Host 实现与客户端本地码（现状差异，v2 必须收敛）

### 7.1 两套 v1 Host 的错误码差异

现状有**两个** Host 实现：Windows 客户端内嵌的、以及独立命令行服务端。协议子集相同，独立实现另有若干码不同（下表为实测差异，不含上表已列的共同码；表中「重新识别时原图已不在主机上」一行是已在 v1 内收敛的历史差异）：

| 场景 | 内嵌 Host | 独立服务端 | 处置 |
|---|---|---|---|
| 停止服务 / 本机命令行端点被非本机调用 | 无该端点 | `403 forbidden`（`只允许本机停止服务` / `只允许本机使用命令行`） | v2：这两类端点**不属于 LAN 协议**，规范里划到「本机控制面」，不列为协议码 |
| 本机控制令牌缺失或错误 | 无 | `403 forbidden`（`缺少或错误的控制令牌`） | 同上 |
| 该实例没有开放本机命令行 | 无 | `501 unavailable` | 同上 |
| 本机命令行请求体形态不对 | 无 | `400 bad_request`（`请求体需要是 {"command": "..."}`） | 同上（注意：与 `invalid_request` 是两个码） |
| 重新识别时原图已不在主机上 | `409 invalid_request`（`原图已不在电脑上，无法重新识别`） | `409 invalid_request`（`原图已不在电脑上，无法重新识别`） | **已统一（v1 内已收敛）**：两端同码同状态，`sync.ndjson` 31 钉住 |
| 队列满的 message | `主机任务队列已满（N），请稍后重试` | `已有识别正在进行，请稍后重试` | message 非契约，客户端只按 `code` 分支 |

**MUST**：客户端分支只看 `code`（不看 `message`、不看具体文案）。**MUST**：v1 期间的客户端必须同时接受上表两种取值 —— 现状 Android 端就是这么做的。

### 7.2 客户端本地合成的码（不在线路上）

客户端在传输层自己合成下列取值，服务端永远不会发送：

| 取值 | 何时产生 |
|---|---|
| `timeout` | 连接 / 读超时 |
| `network_error` | 连不上（主机没运行、不在同一网段、证书问题） |
| `cancelled` | 调用方主动取消 |

WS 侧的 `auth_failed` 同样是**客户端本地**事件（主机从不发送）。

**MUST**：解析响应时若 `code` 缺失，按 `internal` 兜底，不得把「没有 code」当成成功。

## 8. 文档-实现分叉

| 现有文档怎么写 | 实现是什么 | 处置 |
|---|---|---|
| 配对失败表把 `already_paired` 当 `code` | 409 响应体**没有** `code` 字段，`already_paired` 是布尔字段 | 规范写明它是标志而非码；详见 `03-auth-pairing.md` |
| 没有错误码全表（只在配对小节列了 4 个码） | 另有 `queue_full`、`too_many_pages`、`payload_too_large`、`not_found`、`internal` 等 | 本文件首次给出全表；`internal` 标注为「不由端点产生」 |
| `code_expired` 的 `retry_after_seconds` 被描述为等待提示 | 实现给出的是「已过期秒数」（0..60 截断） | 规范写明现状语义，并把它列入 v2 修正项 |
| 错误体示例只展示了 `retry_after_seconds: null` 一个取值 | 该键**恒存在**；不使用 `Retry-After` 头 | 规范写明「键恒在」与「头不用」 |
| 「客户端限流：每分钟 30 次」未写计数口径；未写被拒请求是否计数 | 限流先于体积判定，413 / 400 被拒的上传同样占额度 | 规范写明口径（与 `02-transport.md` 一致） |
| 未区分 HTTP `code` 与任务 `error_code` | 两套取值空间并存，`internal` 是两者共用的兜底值 | 规范要求客户端不得混用两个空间的码 |
| 未写客户端拿到错误码后的重试行为 | 「截屏」入口对除 `revoked` / `no_active_collection` 外的错误码也入离线队列补跑 | 规范按现状写明，并把它列入 v2 收紧项 |
