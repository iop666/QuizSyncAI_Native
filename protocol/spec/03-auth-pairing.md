# 03 鉴权与配对

> 状态：v1 现状（**按实现反推**）+ v2 目标（标注清楚哪句是现状、哪句是 v2 变更）。
> 强制级别：**MUST** = 必须做到；**SHOULD** = 有理由才能偏离；**MAY** = 可选。
> 未标「**v1 现状**」或「**v2 变更**」的条目 = v1 现状且继续有效；本域事实按内嵌服务端形态的实现反推。

## 1. 配对码

- **MUST** 配对码是 **6 位十进制数字**，取值 100000–999999（首位非 0），生成方式等价于「100000 + 0..899999 的均匀随机数」。
- **MUST** 由密码学安全随机源生成；**MUST NOT** 用时间戳、自增序号或可预测伪随机源。
- **MUST** 有效期 **5 分钟**（300000 毫秒），自「生成或刷新」的那一刻起算；过期判定是「当前时刻 **严格大于** 到期时刻」——恰好等于到期时刻仍然有效。
- **MUST** 同一时刻只有一个有效配对码；刷新即换新码，旧码**立即**失效，没有宽限期。
- **MUST** 刷新配对码时把到期时刻重置为「当前时刻 + 5 分钟」。
- **v1 现状** 配对码**不落库**：主机每次启动生成新码，启动时到期时刻 = 启动时刻 + 5 分钟（重启即换码）。
- **v1 现状** 配对成功**不会**让配对码失效——在剩余有效期内它可继续被其它设备使用，只受每分钟 5 次尝试的限流约束。
- **MUST NOT** 把配对码放进任何 HTTP 响应体或响应头（现状：设备自述接口 `GET /api/v1/info` 不含它）；配对码只出现在主机本机界面上。
- **SHOULD** 主机界面显示剩余有效期并每秒重算，剩余 ≤ 0 时提示「已过期，请点刷新」，并提供手动刷新入口；**v1 现状** 进入该界面时会**自动刷新一次**配对码（旧码同时作废）。
- **v1 现状** 配对码只做**字符串相等**比较：服务端不校验长度、也不校验是否为数字，提交任意非空字符串都只得到 `invalid_code`。

## 2. 二维码与配对链接

- **MUST** 主机把配对链接渲染成二维码，内容为文本：

```
quizsync://pair?host=<主机局域网地址>&port=<端口>&code=<配对码>&sid=<主机 device_id>&v=1
```

- **MUST** 客户端只接受以 `quizsync://pair?` 开头的文本，其余一律判为「不是配对链接」。
- **MUST** `host` / `port` / `code` 三项齐全才能解析成功；`sid` 缺失按空串处理。
- **v1 现状** `v` 参数**被客户端忽略**（不作为版本判据，也不校验取值）。
- **MUST** `port` 是主机实际监听的端口（默认 8765，被占用时顺延取 8766–8770 之一，见 `02-transport.md`）。
- **v1 现状** 二维码内容与主机上「复制配对链接」按钮复制的内容是**同一条**链接；取不到局域网地址时 `host` 记为 `127.0.0.1`。
- **MUST** 客户端提供三条配对入口：扫码、粘贴配对链接（读剪贴板）、手动输入地址与配对码。前两条要求文本以 `quizsync://pair?` 开头；手动输入那条在本地先校验配对码长度为 6，不符合时本地报错、**不发请求**。
- **SHOULD** 客户端配对前先调 `GET /api/v1/info` 确认主机身份，并在界面上显示主机名；主机 `ai_configured` 为 false 时只提示、**不阻止**配对。

## 3. 配对流

`POST /api/v1/pair`（**无需鉴权**）

| 字段 | 必填 | 说明 |
|---|---|---|
| `code` | 是 | 主机显示的 6 位配对码 |
| `device_id` | 是 | 客户端设备标识 |
| `device_name` | 是 | 展示名 |
| `platform` | 否 | **缺字段**时按 `android` 处理；显式给空串则校验失败 |
| `app_version` | 否 | 缺字段时按空串处理，仍可通过校验 |

- **MUST** 字段值先转成字符串再校验；请求体不是 JSON **对象**（数组、裸标量、空体、解析失败）→ `400 invalid_request`；`code` / `device_id` / `device_name` 任一为空 → `400 invalid_request`。
- **MUST** 首次配对成功 → `200`：`{"token":"<64 位小写十六进制>","server_device_id":"<主机 id>","server_name":"<主机名>","protocol_version":1}`
- **MUST** 同一 `device_id` **重复配对** → `409`，响应体是上面四个字段**加上** `"already_paired": true`，并且**照发一枚新 token**。
- **MUST** 客户端把 `200` 与 `409` **都按配对成功处理**（都取出 `token` 保存）。`already_paired` 是布尔字段、**不是错误码**；`409` 响应体里**没有** `code` 字段。
- **MUST** 重复配对使旧 token **立即作废**（旧 token 的下一次请求得到 `401 unauthorized`）；设备行的 `paired_at` 保留**首次**配对时间，`name` / `platform` / `app_version` / `last_seen_at` 按新请求覆盖。
- **v1 现状** 重复配对会把 `revoked_at` 清空——被吊销过的设备重新配对即恢复可用。
- **v1 现状** 重复配对**不**断开该设备已建立的 WS 连接；但该设备下一次 WS 握手会顶掉旧连接（同一 `device_id` 只保留最新一条连接）。

## 4. 令牌

- **MUST** token 形态：32 字节随机数逐字节转两位小写十六进制后拼接，恒为 **64 位小写十六进制**（`^[0-9a-f]{64}$`）。
- **MUST** 服务端**只保存 `sha256(token)`** 的十六进制值，落在设备注册表的 `token_hash` 列；明文 token 不落盘、不写日志。
- **MUST** 明文 token 只在配对响应里下发一次；此后**没有任何接口能再查出它**（设备列表与同步快照里的设备 JSON 都不含 `token_hash`）。
- **MUST** 鉴权头为 `Authorization: Bearer <token>`；`Bearer ` 前缀按字面（含大小写）匹配，前缀后内容去首尾空白后为空即视为「没有 token」。
- **MUST** 校验方式：对收到的 token 求 SHA-256，与设备注册表里未吊销设备的 `token_hash` 比对。
- **MUST** 没有 token / token 认不出 → `401 unauthorized`；token 命中但设备已吊销 → `401 revoked`。
- **v1 现状** **token 没有有效期**：设备注册表没有到期列，实现里也没有过期判定。只有两种终结方式——同一 `device_id` 重新配对换新 token，或吊销设备。
- **v2 变更** 为 token 增加可轮换的有效期与显式刷新流程，并在设备注册表落一列到期时间；过期后返回明确错误码（废弃策略见 `09-errors.md`）。

## 5. 配对码与令牌的生命周期

| 事件 | 配对码 | 已签发 token |
|---|---|---|
| 主机启动 | 生成新码，TTL 5 分钟 | 不变（哈希在库，继续可用） |
| 手动/进页面刷新 | 换新码并把 TTL 重置为 5 分钟；旧码立刻失效 | 不变 |
| 配对码到期 | 在刷新前一律 `code_expired` | 不变 |
| 客户端首次配对 | 不受影响（码在有效期内可再用） | 新签发一枚 |
| 同 `device_id` 重新配对 | 不受影响 | 旧 token **立刻作废**，发新 token |
| 吊销设备 | 不受影响 | 该设备 token **立刻失效** → `401 revoked` |
| 主机重启 | 换新码（不持久化） | 不变 |

## 6. 身份与角色

- **MUST（v1 现状）** v1 只有一种身份：**持有未吊销 token 的已配对设备**。协议里没有 host / client 角色字段，服务端不区分「主机自己」与「客户端」。
- **v1 现状（如实记录，不是推荐做法）** `GET /api/v1/devices`、`DELETE /api/v1/devices/<id>`、`POST /api/v1/collections/<id>/select` 等端点**任一已配对设备都能调用**——吊销别的设备也只需要一枚有效 token。
- **v1 现状** 唯一的归属校验在同步 op 推送：op 的 `device_id` 必须等于调用方设备，否则计入响应的 `rejected`；声称由主机产生的 op 被**静默忽略**（不入库，也不计入 `rejected`）。
- **v2 变更** 收紧为角色模型：吊销设备只允许主机自身（或明确的管理角色）调用；主机专属端点需角色校验；越权返回 `403`（该码当前不存在，见 `09-errors.md`）。
- **MUST** 设备注册表字段固定为：`device_id`（主键）、`name`、`platform`（`windows` / `android`）、`token_hash`、`paired_at`、`last_seen_at`、`revoked_at`、`app_version`；`revoked_at` 非空即表示已吊销。
- **MUST** 设备列表**包含**已吊销设备（`revoked_at` 非空），客户端据此显示「已吊销」。

## 7. 同一时间只有一台安卓（v1 现状事实）

- **MUST（v1 现状）** 两端 `device_id` 都是**固定字面量**（主机与客户端各一个常量，不生成 UUID、不随安装或机器变化）。设备注册表以 `device_id` 为主键，于是第二台安卓用同一字面量配对会走「重复配对」分支，**覆盖同一行的 `token_hash`**：第一台安卓的 token 立刻失效（后续请求 `401 unauthorized`），而它只在收到 `revoked`（HTTP）或 `device_revoked`（WS）时才引导重新配对，所以界面表现为「电脑未连接」。
- **MUST** 主机界面给出正确的换机顺序：**先吊销旧设备，再用新手机扫码**；直接配对新手机，旧手机会立刻掉线并需要重新扫码。
- **v2 变更** 客户端设备标识改为每台设备独立生成并持久化，服务端支持多台客户端同时在册；超出上限时用明确错误码拒绝，而不是静默顶掉旧设备。

## 8. 限流与锁定

- **MUST** 配对尝试按**滑动 60 秒窗口**限流，窗口内**最多 5 次**。
- **MUST** 计数口径：请求通过 JSON 与必填字段校验后即计数——**配对成功也计数**；因锁定被拒、或因窗口已满被拒的请求**不计**。
- **MUST** 窗口内超限 → `429 rate_limited`，`message`「尝试过于频繁」，`retry_after_seconds` = 最早一次尝试离开窗口所需的整秒数（向上取整）。
- **MUST** 连续失败 **10 次** → 锁 **60 秒**；锁定期间任何配对请求（**包括配对码正确的请求**）都得到 `429 rate_limited`，`message`「失败次数过多已锁定」，`retry_after_seconds` = 剩余锁定整秒数（向上取整）。
- **MUST** 只有 `invalid_code` 与 `code_expired` 计入失败数；到达阈值时先置锁、再把失败计数归零；配对成功把失败计数归零。
- **MUST** 失败计数与锁定到期时刻**落库持久化**（键 `pair_fail_count` / `pair_locked_until`），主机重启**不清零**；启动装载时若锁定已过期，两个值一起归零。
- **v1 现状** 失败计数是**主机全局一份**（不按 `device_id`、也不按来源地址分桶），任一客户端猜错都会推进同一个计数；计数/锁定的读写失败被忽略（按「没有历史」处理），不影响本次配对结果。
- **v1 现状** 图片上传另有**独立**滑窗限流：每台已认证设备每分钟 30 次，超限同为 `429 rate_limited`、`message`「上传过于频繁」（数值与口径见 `02-transport.md`、`09-errors.md`）。

## 9. 吊销

- **MUST** `DELETE /api/v1/devices/<id>` → `200 {"revoked":"<id>"}`；该调用**幂等**——对不存在的 `device_id` 也回 `200`（不做任何改动）。
- **MUST** 吊销 = 把该设备行的 `revoked_at` 置为非空；`token_hash` 与 `paired_at` **不变**。
- **MUST** 吊销后立刻：向所有已连接客户端广播 `{"type":"device_revoked","device_id":"<id>"}`，随后关闭该设备自己的 WS 连接（**先广播后关闭**，被吊销设备能收到这一条）。
- **MUST** 被吊销设备的后续请求 → `401 revoked`，与「token 认不出」的 `401 unauthorized` **必须区分**；WS 握手失败同样按此区分。
- **MUST** 客户端收到 `revoked`（HTTP）或 `device_revoked`（WS）→ 清除本地配对信息、回到「未配对」并提示重新扫码。
- **v1 现状** 重新配对同一 `device_id` 会清空 `revoked_at`，设备恢复可用（吊销**不是**永久的）。

## 12. 文档-实现分叉

| 现有文档怎么写 | 实现是什么 | 处置 |
|---|---|---|
| `server_device_id` 是「UUID v4，首次启动生成后持久化」 | 两端 `device_id` 都是固定字面量，不生成 UUID、不随安装变化 | 规范按实现写明「固定字面量」，并把 UUID 化列入 v2 |
| 「除配对外所有请求都要 token」 | `/api/v1/info` 也免鉴权；`/ws` 上版本协商不生效（见 `02-transport.md`） | 规范写明免鉴权路径是「配对 + 设备自述」两条 |
| 未提第二台客户端的影响，也未提「配对码不失效」 | 同 `device_id` 覆盖 `token_hash`；配对成功后配对码可继续使用 | 规范写明换机顺序与「码可复用」；v2 分别改为每设备独立标识、一次性码 |
| 未提限流与锁定的持久化 | 失败计数与锁定到期时刻落库，重启不清零 | 规范补写「跨重启有效」是硬要求 |
| 未提重复配对会清空 `revoked_at` | 重新配对即恢复被吊销设备 | 规范写明现状；是否允许「吊销可被自助解除」列入 v2 |
| 把 `already_paired` 列在配对的失败表里当 `code` | 409 响应体无 `code` 字段，`already_paired` 是布尔字段 | 见 `09-errors.md`（错误码域） |
